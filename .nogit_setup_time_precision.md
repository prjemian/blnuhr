# Setup-Time Precision Investigation

## Problem statement

In the Arduino clock project, entering the setup screen allows the user to
change the hour and minute. The seconds, and possibly the sub-minute timing,
appear to remain frozen at the time setup was entered. When the user accepts
the new hour and minute, the clock is therefore written with stale seconds
and loses up to nearly one minute of accuracy each time setup is used.

The desired result is that changing hour and minute does not reset or freeze
the seconds. Accepting the setup should preserve the current seconds, or use
the current clock time at the instant the new hour and minute are committed.
Sub-minute precision should also be preserved when the hardware and clock
API support it.

## Repository investigation

The setup screen currently visible in `arduino-TFT2/my_tft_button_demo.ino`
is development code:

- The displayed hour and minute are placeholder values.
- The setup screen has no connection to the DS3231 object.
- The `OK` handler contains a TODO instead of an RTC write.
- The sketch has no current seconds or milliseconds value to preserve.

The RTC and temperature display are in the separate
`arduino-TFT2/arduino-TFT2.ino` sketch:

- It reads the DS3231 through `Rtc.GetDateTime()`.
- It displays the DS3231 temperature.
- It has no setup-screen editing or `OK` commit path.

The complete setup implementation is therefore likely in another Arduino
project or working copy and must be located before changing firmware here.

## Correctness ideas

1. On entry to setup, capture the current date/time as the editing baseline,
   but do not use that captured value as the final seconds value.
2. Keep hour and minute as editable fields only.
3. On every setup-screen update, obtain the current clock time or track elapsed
   time from the setup baseline.
4. On `OK`, construct the new date/time from the selected hour and minute plus
   the current seconds. If supported, include current sub-second precision.
5. Write the RTC once, at acceptance, rather than when setup begins.
6. Define rollover behavior explicitly. If setup crosses a minute boundary,
   the accepted hour/minute should be combined with the current seconds from
   the same reading used for the commit.
7. Test entering setup and accepting without changing the displayed hour or
   minute. The clock should not lose the time spent in setup.
8. Test changing only the hour and only the minute, including acceptance just
   before and just after a minute boundary.

## Open questions

- Which Arduino project contains the actual RTC-backed setup screen?
- Does its RTC library expose sub-second precision, or only whole seconds?
- Should `OK` use the current seconds, force seconds to zero, or provide a
  deliberate seconds-setting control?
- Is the `millis` value an RTC sub-second value or elapsed Arduino time used
  to maintain a software clock?
